# 手順（#37 T4）: 工程設計の引き継ぎ・手順の正本・設計の画面

状態: **設計の提案（実装前）**。Issue #37、設計 [editor-niho-life-design.md](editor-niho-life-design.md) §7.2、実行基盤 [editor-steps-execution.md](editor-steps-execution.md)。

旧 NIHO docs の工程設計（`packages/docs-core`）を editor.niho.life へ引き継ぐときの、(1) 手順の正本をどこに置くか、(2) 段階の実行からサブページの生成までで何が足りないか、(3) 手順を作る・直す画面をどこに置くか、(4) 旧アプリから落としてはいけない振る舞い、の 4 つを決める。コードは含まない。

実装の前提として **T1（`recipes` の表）と T5（本物の実行器）**を待つ。この文書はその 2 つと噛み合う形を決めるためのもの。

**T5 の実行器の口は届いた**（2026-11-01）。`StepExecutor` の形は変わらず、T4 側の変更は要らない。増えたのは任意の `owner` の欄と、**段階の失敗の code 11 個**で、後者は見せ方を決める必要がある（§2.5）。

いちばん大きな発見を 3 つ先に書く。

1. **手順の編集の画面は、もう有る。** #108（PR #110）が設定に「手順」の節を作り、段階の名前・指示・お手本（文書ガイド）の編集、段階の追加・削除、手順の複製・追加・削除・既定に戻す、までを実装済み。§7.2 が言う「設定の『手順』で編集・追加・複製できる」は満たしている。T4 が作るのは**その節の続き**で、別の画面ではない。
2. **実行の仕組みは完成しているが、段階に渡している入力が足りない。** `readStepInput` は「録音ページ ＋ 直前の段階のサブページ」の 2 つだけを返す。docs-core の入力の規則（`inputs.ts` の `inputsFor`）は「原文 ＋ **段階 1〜N−1 の全部**の成果物 ＋ 参考ページ ＋ 背景情報 ＋ 文書ガイド」。記事制作の「記事本文」が「記事方針」だけを見て「文字起こし修正」を見ないので、**いまの形のまま本物の AI を繋ぐと記事の質が落ちる**。T5 より先にここを直す。
3. **最後の段階は、いまのままでは「そのまま公開」できない。** 設計 §7.2 は「最後の段階（記事本文）はそのまま公開できる」と言うが、サブページの題名は段階の名前（「記事本文」）のままで、作ったあと誰も更新しない。公開はこの題名を使い、URL の slug も題名から作る（`slugFromTitle` は英数字以外を落とすので「記事本文」は `p-1a2b3c4d` のような id に落ちる）。**題名「記事本文」・URL が id の記事が公開できてしまう**。→ **公開のシートの条件で人に入れさせる**ことに決まった（§2.6）。

## 1. docs-core の工程設計を `recipes` の表にどう載せるか

### 1.1 いま手順はどこにあるか（正本が 2 つになる）

| 置き場 | 入っているもの | 状態 |
| --- | --- | --- |
| `packages/docs-core/src/templates.ts` の `FLOW_TEMPLATES` | 既定の 4 つのテンプレート（記事制作・議事録・インサイト整理・コーチング）の**指示文の正** | main に有り。editor は `tpl-1`〜`tpl-3` の 3 つを `DEFAULT_RECIPES` に写している（`apps/editor-web/src/steps/recipes.ts`） |
| `editor_settings.recipes`（jsonb。migration 0013） | 既定に手を入れた写しと、足した手順（`{ id, name, guide, steps: [{ id, name, instruction }] }`） | **main に有り。設定の画面・受付 API・worker が既に読み書きしている** |
| `recipes` の表（T1 の `0021_recipes.sql`） | 工程・プロファイル・guide・固有名詞・お手本 | 作成中 |

`editor_settings.recipes` が既に動いているので、T1 の表が入ると**同じものの正本が 2 つになる**。放っておくと、設定の画面が jsonb を書き、実行が表を読む（またはその逆）形になり、「設定で直したのに実行に効かない」が起きる。

### 1.2 判断: `recipes` の表を正本にし、`RecipeReader` の 1 か所で差し替える

**理由。** 表に移す理由は 1 つだけで、**お手本の文書（`samples`）の本文を入れるため**。docs-core の上限は 1 本 30,000 字 × 5 本（`rules.ts` の `SAMPLE_MAX_CHARS`・`SAMPLE_MAX_COUNT`）＝ 手順 1 つで最大 150KB。これを `editor_settings` の jsonb に入れると、**`GET /api/pages/{id}/steps` が数秒おきに読む**（前提変更の測り直しで `deps.recipes()` を呼ぶ）行が最大 3MB（手順 20 個分）になる。帯を開いている間ずっとそれを引くのは割に合わない。固有名詞と revision も表の方が素直に入る。

**移すときの救い**は、`recipes.ts` が既に `RecipeReader = (owner) => Promise<readonly RecipeDef[]>` という口を切っていること。置き場を替えても変わるのは `apps/editor-web/src/server/steps-deps.ts` の `ownerRecipes()` **1 関数**で、受付 API・worker・runner・画面は触らない（#108 がこの口を作ってくれた形がそのまま効く）。

**ただし 1 か所、口を通っていない読み手がある。** 開発・CI の inline 実行の `createInlineQueue`（同じ `steps-deps.ts`）は、`recipes:` に自分用の reader を渡し、`getEditorSettings(pool, owner).recipes` を直接読んでいる。`ownerRecipes()` だけ替えると、受付 API は新しい表の定義を読み、inline の実行は古い jsonb の定義を読む（または新しく作った手順が見つからない）形になる。**移すときは、この reader も `ownerRecipes()` を使うようにして、読み手を 1 つにする**（移行の範囲に含め、受付 API と inline の実行が同じ手順を見ることをテストで固定する）。

なお §2.7 で run に手順の写しを固定すると、**実行の側は `RecipeReader` を読まなくなる**（写しで走る）。この二重の読み手の問題は写しが入れば消えるが、**写しより先に表へ移すなら、上のとおり読み手を 1 つにしてから移す**。

**`samples` は hot path から外す。** お手本の本文は `recipe_samples`（別の表か、同じ表の別の列）に置き、`RecipeDef` には**名前と字数だけ**を載せる。本文を読むのは (a) 文書ガイドの抽出のとき、(b)（もし入力に入れるなら）段階の実行のとき、の 2 つだけ。帯の polling では読まない。

### 1.3 docs-core の `Flow` と `recipes` の表の対応

| docs-core `Flow` | `recipes` に載せるか | 理由 |
| --- | --- | --- |
| `id`・`name` | 載せる | そのまま |
| `revision`（保存のたびに増える） | **載せる（必須）** | §2.7 の写しの固定で、帯が「手順が新しくなっています」を出すのに使う。**版を比べるだけで済むので要求も問い合わせも増えない** |
| `guide`（文書ガイド。Markdown） | 載せる（既に `editor_settings` に有る） | 全段階の入力に入る |
| `terms`（手順ごとの固有名詞 4 列） | **載せる** | いま editor はアカウント共通の `editor_settings.glossary` だけ。docs-core は手順ごとと案件ごとの 2 段。§3.3 で相談 |
| `samples`（お手本の文書） | 載せる（本文は別の表） | §1.2 |
| `transcription`（先頭に文字起こし工程を含むか） | **載せない** | editor は録音ページの下にサブページを作る形で、文字起こしは #36 の別経路。手順の段階に文字起こしは含まれない（`recipes.ts` の既定 3 つも含まない） |
| `steps[].id`・`name`・`instruction` | 載せる | そのまま |
| `steps[].profile`・`provider`（モデル × 思考量） | **載せない** | editor はモデルと鍵をサーバー側だけに置く設計（`apps/editor-web/src/ai/config.ts` の `resolveAiBackend(env)`、設計 §6）。段階ごとに提供元を選ぶ UI も持たない。docs-core の `Profile`・`ResolvedStepModel`・`FlowSnapshot.models` は editor には要らない |

**`ProjectInfo`（背景情報・登場人物・話者人数・言語）は手順ではなく録音ページ側**。いま editor の録音ページはこれを持たない（§2.2 G）。

### 1.4 T1 へのお願い（表を作る側に渡すこと）

1. `recipes` は **owner ごと**（`owner text` + `id text` の複合主キー）。既定の 3 つは行を作らず、**手を入れたものと足したものだけ**が行になる（いまの jsonb と同じ考え。`recipesOf()` が既定にかぶせる）。
2. `0021` で **`editor_settings.recipes` の中身を `recipes` の行へ移す**（jsonb → 行）。列はその migration では落とさず残し、読まなくする（切り戻しのため）。落とすのは次の節目で。
3. お手本の本文は `recipes` の行に入れない（§1.2）。
4. 上限は docs-core と editor で食い違っているので、**表の CHECK は editor 側の値に合わせる**。食い違い: 文書ガイド 20,000 字（editor）対 4,000 字（docs-core `GUIDE_MAX_CHARS`）、段階 12（editor）対 32（docs-core `FLOW_MAX_STEPS`）。値の正は `packages/editor-store/src/settings.ts` の `SETTINGS_LIMITS` 1 か所のままにする。
5. 新しい表を足したら `packages/editor-store/test/store.integration.test.ts` の `documented` の一覧にも足す（忘れると CI が落ちる。#108 が 1 回踏んでいる）。

T1 が別の形で先に入った場合は、T4 が `ownerRecipes()` をその形に合わせる。**表の形の相談は T1 の PR で行い、T4 は migration の番号を取らない。**

### 2.3 入力の規則を直す形（B）

docs-core の規則（`inputs.ts` の `inputsFor`、spec §5.1）:

> 段階 N の入力 ＝ 原文（文字起こし／文章）＋ 段階 1〜N−1 の成果物（最新版）＋ 参考ページ ＋ 背景情報 ＋ 文書ガイド

直す形:

- `readStepInput` の答えを `{ parentBlocks, upstream: { stepIndex, stepId, name, blocks }[] }` にする（`previousBlocks` は `upstream` の末尾になるので畳む）。`step_attempts` は run の全段階の `page_id` を持っているので、**読み出しは 1 問い合わせのまま**（`page_id` の配列で `pages` を引く）。
- `StepExecutorInput` に `upstream` と `guide`・`glossary` を足す。`recipe` は既に渡っているので `guide` はそこから取れる。
- 上流のサブページが**人に消されていた**ら、その段階は空として渡す（止めない）。基準の計算では空文字として扱う（docs-core `basisFor` が `materials.artifacts[step.id] ?? ""` を hash するのと同じ）。

これは `packages/editor-store/src/step-runs.ts` の読み出し 1 関数と `apps/editor-web/src/steps/executor.ts` の型の変更で、**実行の制御（世代・lease・確定）には触らない**。

### 2.4 前提（basis）を docs-core の形に広げる（C）

いま `step_attempts.input_basis` は 64 文字の sha256 1 つで、`refreshStale` はそれが一致するかだけを見る。これで「前提変更」の印は出せるが、**何が変わったのか**を言えない。

旧アプリは `staleNoticeText` で本文の上に 1 行出す: 「元の文字起こしが変わりました。」「背景情報が変わりました。」「文書ガイドが変わりました。」「工程の指示が変わりました。」。**これは落とせない**（§4）。帯が「前提変更」とだけ言って、何を直したせいか分からないのは、作り直すかどうかを決められない。

直す形:

- `input_basis` を**項目ごとのハッシュを持つ jsonb** にする（docs-core の `Basis` と同じ形: `source`・`artifacts`・`info`・`guide`・`step`、`refs` は持たない）。
- 比較は docs-core の `staleReasons` を**そのまま使う**（純粋な関数で、editor の `Block[]` を hash した文字列を入れるだけ）。文言も `staleNoticeText` をそのまま使う。
- `refreshStale` は `boolean` ではなく**理由**を返し、`GET /api/pages/{id}/steps` の答えに段階ごとの理由を載せる。帯は**色だけで状態を表さない**（文字で理由を出す）ので、むしろ要件に素直。
- 列の型が変わるので **migration が要る**。§2.7 の写しの列 2 つと**同じ migration にまとめる**（`step_attempts.input_basis` の型 ＋ `step_runs.recipe_snapshot`・`recipe_revision`）。番号は **0023**（オーナー 2026-11-01）。

**互換**: 既存の 64 文字の文字列が入っている行は「記録が無い」として扱い、前提変更にしない（docs-core の `staleReasons` が `recorded` 無しで `[]` を返すのと同じ）。既に出荷している帯を、移行の瞬間に全部「前提変更」にしない。

### 2.5 段階の失敗の code の見せ方（方針）

T5 の実行器で code が 11 個増える。**文言はここに書かない**（帯の文言は `apps/editor-web/src/lib/steps-view.ts` の
`REASONS` に有り、そのファイルは PR #114 の中でまだ main に無い。#114 を持っているセッションが書く）。ここで決めるのは
**どの code をどちらの群として見せるか**だけ。

#### 2 つの群で言い方を分ける

| 群 | 利用者にとっての意味 | 帯の言い方 | できること |
| --- | --- | --- | --- |
| **再試行する** | 待てば直る。runner が自動で積み直す（試行 3 回まで） | 「〈段階名〉がうまくいかなかったので、やり直しています」 | 待つ。3 回とも失敗したら下の群と同じ扱い |
| **再試行しない** | 人が直すまで直らない | 「〈段階名〉を作れませんでした。〈理由〉」 | 理由ごとに違う（下の表の「次の一手」） |

| code | 群 | 次の一手 |
| --- | --- | --- |
| `ai_unavailable` | しない | 設定の問題。利用者ではなく**運用**が直す。帯は「いまは AI を使えません」と言い、やり直すボタンを出さない |
| `quota_exceeded` | しない | 今月の上限。**設定の「使用量」へ**（上限を上げるか来月まで待つ）。`[fake]` でなく実際にモデルを呼ぶ前に止めているので、費用は増えていない |
| `invalid_output` | しない | AI の答えが本文にならなかった。**やり直す**が効く（同じ入力で結果が変わる） |
| `ai_auth`・`ai_bad_request` | しない | 運用が直す。`ai_unavailable` と同じ見せ方でよい（利用者に鍵・要求の話をしない） |
| `usage_unavailable`・`ai_rate_limit`・`ai_overloaded`・`ai_server`・`ai_timeout`・`ai_network` | する | 待つ。3 回とも失敗したら「時間をおいて、やり直してください」 |
| 既存: `unknown_recipe`・`unknown_step` | しない | 手順が変わった。設定の「手順」を見るか、作り直す |
| 既存: `input_missing`・`page_missing` | しない | 上流のページが消えている。その段階から**作り直す** |
| 既存: `lease_expired`・`internal` | する | 待つ |

#### いま見つかっている取り違え（#114 を持っているセッションへ）

帯の `REASONS` と、実際に投げている code が食い違っている。T5 の 11 個を足す前に直したい。

- **対応表に無い**（帯が理由を言えない）: `unknown_recipe`・`input_missing`・`page_missing`。production で実際に投げている
  （`apps/editor-web/src/steps/runner.ts`）。
- **対応表に有るが投げていない**: `invalid_input`。production のどこからも投げていない（`input_missing` の書き損じと思われる）。
- `fake_failure` は偽物の実行器だけが投げるので、対応表に入れなくてよい。

#### 増やすときに守ること

- **code は短い英小文字だけ**（本文・プロンプト・内部の情報を入れない）。`executor.ts` の `StepError` のコメントのとおり。
- **editor-store 側の変更は要らない。**`isStepErrorCode` と `step_attempts.error_code` の CHECK は形
  （`^[a-z0-9_]{1,64}$`）だけを見ていて、固定の一覧を持たない。T5 の 11 個はそのまま通る。
- **知らない code は言葉にしない**（`steps-view.ts` の `reasonOf` が空文字を返す今の形を守る）。将来 code が増えても
  帯が英語の内部表現を利用者に見せない。
- **状態を色だけで表さない。**「失敗」も「やり直しています」も文字で言う。

### 2.6 最後の段階の題名は、公開のシートで入れさせる（決定）

**決定: 案 (c)**（オーナー 2026-11-01）。実行器は題名を返さない（**T5 の口に `title` の欄は足さない**）。公開のシートの
「公開の前に」の条件に足し、**題名は人が決める**。

#### いまの形

- サブページの題名は `createRun` が段階の名前（「記事本文」）で作り、`commitAttempt` は題名を更新しない。
- 「公開の前に」の条件は `packages/editor-publish/src/readiness.ts`（`collectFacts` が事実を集め、`evaluateReadiness` が
  純粋に判定する）。**題名の条件は既に有る**: `BUILTIN_PROBLEMS.title`（`{ id: "title", message: "題名を入れてください", fix: "body" }`）。
- ただし発火は `if (facts.title === "")` の**空のときだけ**。「記事本文」は空でないので**通ってしまう**。

#### 足すもの

1. `ReadinessFacts` に「題名が段階の名前のまま」を表す事実を 1 つ足す。
2. `BUILTIN_PROBLEMS` に対応する 1 件を足す（`fix` は既存の題名の条件と同じ行き先で足りる）。
3. `evaluateReadiness` に 1 行足す。純粋な関数のままで、発信先の宣言（`declaration.ts`）には触らない
   — **どの発信先でも題名は要る**ので、発信先が宣言する条件ではなく組み込みの条件にする。

#### 段階の名前をどう知るか（表を増やさずに済む）

公開のシートは手順を知らないが、**サブページの id が段階の番号を教えてくれる**。`stepPageId(parent, recipe, stepIndex)`
は決定的なので、ページの行が持っている `parent` と `recipe` から `stepIndex` を 0 から順に当てれば、そのページが何番目の
段階かが分かる（手順の段階の数は 12 まで）。番号が分かれば、その人の手順（`RecipeReader`）から段階の名前が引ける。

「題名を人が直したか」を覚える列（`title_edited`）を足す案は、**migration が要るので採らない**。上の比較で足りる。

#### 残る穴（受け入れる）

利用者が題名をわざと段階の名前と同じ「記事本文」にしたら、公開できない。**受け入れる**（記事の題名として「記事本文」は
まず無い。空の題名を断る今の条件と同じ割り切り）。

#### 画面の言い方

「題名を入れてください」とは別の文にする（空ではないので、利用者には何を直すのか分からない）。文言は公開のシートを
持っているレーンに合わせる。**状態を色だけで表さない**のは今の「公開の前に」と同じ。

### 2.7 手順の写しを run に固定する（決定）

**決定: 旧アプリ通り固定する**（オーナー 2026-11-01）。手順を直しても、既に走らせた録音の結果は勝手に変わらない。変えるときは
**何が変わるかを見せてから、人が明示的に更新する**。

#### いまの形（固定されていない）

`recipes.ts` のコメントは「進行中の run は claim したときの定義で続く」と書いているが、**実際は段階ごと**に読んでいる。
`runner.runAttempt` は毎回 `deps.recipes(claim.owner)` を呼ぶので、

- 3 段階の run の途中で手順を直すと、**段階 2 以降は新しい定義で走る**。
- 掃除が積み直した段階も、積み直した時点の定義で走る。

固定するとこれも直る（run は自分の写しで走り切る）。**コメントの書き換えも要る。**

#### 置き場: `step_runs` に写しの列を 1 つ（表の変更 1 件）

`step_runs` に `recipe_snapshot jsonb NOT NULL`（段階の名前・指示・お手本。**お手本の文書の本文は入れない** — §1.2 と同じ理由）
と、`recipe_revision integer`（どの版から取ったか。帯で「新しくなっています」を出すのに使う）を足す。

**新しい表は作らない。**旧アプリは録音（`Recording.flowSnapshot`）に持っていたが、editor では run に持たせる方が良い:

- run の行が**自己完結**する。worker は `RecipeReader` を読まずに写しで走れる（上の race が消える）。
- 親ページは**手順ごとに別のサブページを持てる**（`stepPageId` が recipe で鍵を分けている。`step_runs_active_idx` は
  `(owner, parent)` なので同時に 1 本だけだが、終わった run は手順ごとに並ぶ）。写しを親ページに 1 つ置くと手順ごとに分けられない。

#### 固定の単位は「親ページ × 手順」

run ごとに今の設定から取り直すと**固定にならない**（「作り直す」で新しい定義になってしまう）。そこで `createRun` は

1. 同じ `(parent, recipe)` の**いちばん新しい run があれば、その写しを引き継ぐ**。
2. 無ければ（その録音でその手順を初めて使う）**今の手順から写しを取る**。

これで「一度始めたら、明示的に更新するまで固定」という旧アプリの振る舞いになる。

#### 「今の設計に更新」は写しを差し替えるだけ

**再実行はしない。**写しを今の手順で差し替えると、指示文が変わった段階の `Basis.step`（§2.4 で項目ごとに持つようにする
もの）が食い違い、**その段階が自然に「前提変更」になる**。あとは今ある「作り直す」で走る。旧アプリも同じ組み合わせ
（`Basis.step` のコメント「工程設計を直して『この案件の工程を今の設計に更新』したとき、指示文が変わった工程に stale を出す」）。

つまり**新しい実行の仕組みは要らない**。要るのは「写しを差し替える」操作 1 つと、その前に見せる差分。

#### 差分の見せ方

帯に 1 行出す（例: 「手順が新しくなっています」）→ 押すと何が変わるかを見せる → 「更新する」で写しを差し替える。
出す項目は旧アプリの `FlowDesignDiff` と同じで、editor が持つものだけ: **増えた段階・消えた段階・名前が変わった段階・
指示文が変わった段階・並びが変わった・お手本が変わった**（`models`・`transcription` は editor に無い。§1.3）。

**docs-core の `diffFlowDesign` は直接呼ばず、editor-web に同じ形の小さな関数を置く。**`diffFlowDesign` は `Flow`
（`terms`・`samples`・`revision`・`profile` を持つ）を取るので、`RecipeDef` から偽の `Flow` を組むことになる。docs-core は
Mac アプリと共用で他のレーンも触るため、**こちらの都合で広げない**。docs-core 側は項目の並びと言葉の参照元として使う。

#### いつ出すか

`recipe_revision` と今の手順の `revision` が違うときだけ（T1 の表に `revision` が要る理由。§1.3）。`revision` を比べるだけなので、
`GET /api/pages/{id}/steps` が既に読んでいるもので足り、**要求も問い合わせも増えない**。差分の中身は押したときに作る。

#### 既にある run（移行）

列を足した時点の run には写しが無い。**その run は「今の手順」を写しとして埋める**（migration の中で `editor_settings.recipes`
から、または既定の手順から）。帯に「新しくなっています」が一斉に出ないようにするため、`recipe_revision` も同じ時点の版で埋める。

#### 大きさ

写しは最悪で 116KB ほど（お手本 20,000 字 ＋ 段階 12 × 指示 8,000 字）だが、既定の手順ならふつう数 KB。`step_runs` の行は
消えない（親ページが消えるときに CASCADE で消えるだけ）ので、「作り直す」を繰り返すと積もる。**実害が出る量ではない**が、
気になるなら写しが前の run と同じなら前の run を指す形にできる（v1 ではやらない）。

| 12 | **途中までの出力を捨てない**（版にせず checkpoint に残す） | `types.ts` `RunCheckpoint` | × 失敗すると何も残らない | **§6 E: F と一組で限って入れる** |
| 13 | **成果物の題名が成果物自身から決まる**（記事の題名は本文の H1。手順の段階の名前ではない） | `templates.ts` の記事制作のガイド「タイトル: 内容の核心を 30 字前後で表す」、`types.ts` の「本文H1」 | × **サブページの題名は段階の名前のまま**（`createRun` が `step.name` で作り、`commitAttempt` は題名を更新しない） | **§2.6（決定）**: 公開のシートの条件で人に入れさせる |
| 14 | **手順を直しても、既にできている録音の結果は勝手に変わらない**（録音が作成時の写しを持つ） | `types.ts` `FlowSnapshot`、`Recording.flowSnapshot` | × **段階ごとに今の定義を読む**（run の途中で直すと段階 2 以降が新しい定義で走る） | **§2.7（決定）**: run に写しを固定する |
| 15 | **手順を直したら、何が変わるかを見せてから更新する**（増えた・消えた・名前・指示文・並び・文書ガイドの違い） | `flow-edit.ts` `diffFlowDesign`・`FlowDesignDiff` | × | **§2.7（決定）**: 帯に出し、写しを差し替える |

14 と 15 は一組で、**旧アプリ通り固定することに決まった**（オーナー 2026-11-01）。設計は §2.7。`step_runs` に列 2 つを足すだけで、新しい実行の仕組みは要らない（写しを差し替えると、指示文が変わった段階が既にある「前提変更」の仕組みで拾われる）。

## 5. 進め方（T1 と T5 が入ってから）

1. **入力の規則と前提**（§2.3・§2.4）。本物の AI の前に、偽物のままで「上流の全部を読む」「理由の出る前提変更」を通す。帯に理由が出るところまで。
2. **`recipes` の表へ寄せる**（§1.2）。`ownerRecipes()` の差し替えと、設定の API の読み書きの付け替え。画面は変えない。
3. **お手本の文書と文書ガイドの抽出**（§3.3）。取り込み（ファイル・URL）→ 抽出 → 確かめて置き換え。
4. **設計の画面の続き**（並べ替え・段階の複製・重ならない名前・実行できない印）。
5. **本物の実行器**（T5）と繋ぎ、記事制作を最後まで通す。この前に、帯の対応表の取り違え（§2.5）を #114 を持っているセッションが直し、T5 の 11 個の code を足す。
6. **手順の写しの固定と差分**（§2.7）。§2.4 の前提の jsonb と**同じ migration にまとめる**（列 3 つ: 写し・版・前提）。
7. **公開のシートの題名の条件**（§2.6）。`readiness.ts` に事実 1 つ・条件 1 件・判定 1 行。文言は公開のシートを持っているレーンに合わせる。最後の段階をそのまま公開できるようになって、§7.2 の約束が揃う。
8. 残り（手順ごとの固有名詞・録音ごとの背景情報・参考ページ）は §6 の答え次第。

## 6. 残りの相談と、私の推奨

方針は「**できるだけ NIHO docs（旧アプリ）を踏襲する**」（オーナー 2026-11-01）。それに沿った推奨を各件に付けた。
**7 件のうち 5 件は踏襲を推奨**、1 件は形を変えて踏襲、1 件だけ踏襲しないことを薦める。

### 決まったもの

| 件 | 決定 |
| --- | --- |
| 最後の段階の題名 | **(c) 公開のシートで人に入れさせる**（§2.6） |
| 手順を直したときの既存の録音 | **旧アプリ通り固定する**（§2.7） |
| migration の番号 | **0023**。前提の jsonb と写しの列をここに入れる |

### A. 背景情報・登場人物・案件の固有名詞 → **フォルダに持つ（踏襲）。T1 のフォルダ待ち**

旧アプリの `ProjectInfo`（背景情報・登場人物・固有名詞）は**案件（＝フォルダ）**に付き、その中の録音が受け継ぐ。
editor でも**フォルダに持つのが踏襲**で、録音ページごとに持つのは旧アプリと違う（同じ案件の録音で背景情報を書き直す手間が増える）。
フォルダの木は T1 なので、**T1 の後**。

**話者人数（`SpeakerMode`）は要らない。** 旧アプリはこれを文字起こしの手がかりと背景情報の節に使っていたが、editor の
`page_recordings` は既に **`language`** と **`speaker_names`（話者番号 → 名前）** を持っている。docs-core の「文字起こし修正」の
指示文が求めているのは「背景情報の話者の対応表にある番号だけ名前に置き換える」で、**対応表そのものは既にある**。
人数の見込みより対応表の方が役に立つので、`speaker_names` を背景情報として渡す。

**いま 0023 でやること**: 前提（`Basis`）に `info` の欄を置いておく（中身は当面アカウント共通の固有名詞だけ）。
docs-core と同じで「記録が無い欄は比べない」ので、あとでフォルダの背景情報を足しても**migration をもう一度やらなくて済む**。

### B. 手順ごとの固有名詞 → **足す（踏襲）。T1 の表に jsonb 1 列**

旧アプリは固有名詞を 2 段（`Flow.terms` ＝ 手順ごと、`ProjectInfo.terms` ＝ 案件ごと）持ち、`mergeGlossaries` で混ぜる
（同じ表記は**案件ごとが勝つ**）。editor にはアカウント共通の `editor_settings.glossary` があるだけ。

踏襲して**手順ごとを足す**。T1 の `recipes` の表に `terms jsonb` を 1 列で、§1.3 に既に書いてある。
混ぜる順は **フォルダ（案件）→ 手順 → アカウント共通**（先が勝つ。docs-core の `mergeGlossaries` の順にアカウント共通を
いちばん弱い既定として足す）。アカウント共通は旧アプリに無い層だが、**既に出荷して AI の箱が使っている**ので残す。

### C. 参考ページ → **踏襲して入れる。T1 のフォルダ待ち**

旧アプリは「同じフォルダの独立文書を実行時に自動で固定」して段階の入力に入れ、`refsHash` で前提にも入れていた
（`Recording.refs` の手動指定は旧版で、新しい工程は自動）。これはフォルダの木（T1）があれば再現できる。

**いま 0023 でやること**: 前提に `refs` の欄を置いておく。docs-core の `staleReasons` は
「記録が無い＝参考なし」と比べる作りなので、**あとで足しても既存の run が一斉に前提変更にならない**。A と同じ理由で、
今入れておくのがいちばん安い。

### D. 既定の手順の段階の並べ替え → **許す（踏襲）。ただし「今の設計に更新」で守りを付ける**

**根っこに踏襲できていない所がある。** 旧アプリは成果物を**段階の id** で引く（`artifacts/<stepId>.md`。`flow-edit.ts` の
「工程の id は成果物のファイル名になるので、名前を変えても id は変えない」）。editor は **段階の番号（index）** で引く
（`stepPageId(parent, recipe, stepIndex)`）。だから既定の手順は段階の数を変えられない。

id で引く形に直すのが本当の踏襲だが、**既に作られたサブページの id が変わる**（版・共有・公開がその id を指している）ので、
後から変えられない。**負債として記録して、index のままにする。**

そのうえで並べ替えは**許せる**。§2.7 の写しのおかげで、**既存の録音は自分の写し（古い並び）で動き続ける**ので、
手順を並べ替えても壊れない。危ないのは「今の設計に更新」で並びが変わるときだけ（番号 0 の中身が段階 A なのに、
新しい写しでは番号 0 が段階 B になる）。ここは `FlowDesignDiff.reordered` が旧アプリでも警告していた所で、
**並びが変わり、かつ既に結果のある段階があるときは、更新の後にその段階から作り直す必要があることを言う**。

### E. 途中までの出力 → **F と一組で、限って入れる（形を変えて踏襲）**

旧アプリは `RunCheckpoint` に途中までの出力・続きの回数・終了理由を残し、版にしないで保つ。editor は失敗すると何も残らない
（`commitAttempt` は全部か無し）。

**丸ごとの踏襲は薦めない。** 旧アプリの checkpoint は「本人の Mac で長く走る CLI の会話を、手で止めたり再開したりする」ための
もので、editor の段階は 30 分以内の 1 要求 ＋ 自動の再試行 3 回。失敗の形が違うので、会話の id や再開のための情報は要らない。

**ただし F（続き）を入れるなら、「8 回使い切ったときの途中までの出力」だけは残したい**（捨てると長い文字起こし修正が丸ごと無駄になる）。
`step_attempts` に `partial_blocks jsonb` を 1 列。**0023 に入れられる**ので、F と一緒に決めてもらえると migration が 1 回で済む。

### F. 出力が切れたときの続き → **踏襲して入れる。必須に近い**

旧アプリは `MAX_CONTINUATIONS`（8）・`CONTINUATION_INSTRUCTION`・重なり 400 字で続きを繋ぐ。届いた T5 の口は 1 往復。

**これは入れるべき。** 記事本文は 2,000〜3,000 字なのでふつう切れないが、**記事制作の最初の段階「文字起こし修正」は
「出力は要約ではなく、後続の工程で全文を参照するための修正版」**（docs-core の指示文）で、1 時間の録音なら 2 万字を超える。
**ここは確実に出力の上限に当たる**ので、続きが無いと記事制作が最初の段階で壊れる。

`packages/docs-core/src/continuation.ts` は `rules.ts` の定数しか import しない**純粋な部品**（`continuationOverlap`・
`joinContinuation`・`buildFreshContinuationPrompt`）なので、**そのまま使える**。入れる場所は実行器の中（T5 のファイル）。

### G. 複数案（1 つの段階に対等な案を複数） → **v1 に入れない（別 Issue）**

旧アプリの `ArtifactCandidate`・`CandidateSet`。サブページ id が `(親, 手順, 段階)` から決定的に 1 つ決まる editor の前提と
噛み合わない（D と同じ根っこ）。**踏襲しないのではなく、順番を後にする。**

### 0023 に入れる列（決定分 ＋ 推奨分）

| 列 | 何のため | 状態 |
| --- | --- | --- |
| `step_attempts.input_basis` を jsonb へ | 前提の項目ごとの比較と理由（§2.4）。欄は `source`・`artifacts`・`info`・`guide`・`step`・`refs` | 決定 |
| `step_runs.recipe_snapshot jsonb NOT NULL` | 手順の写しの固定（§2.7） | 決定 |
| `step_runs.recipe_revision integer` | 「手順が新しくなっています」の判定（§2.7） | 決定 |
| `step_attempts.partial_blocks jsonb` | 続きを使い切ったときの途中までの出力（E・F） | **推奨**。F を入れるなら |

`info` と `refs` の欄は**中身が空でも今から置く**（A・C）。あとでフォルダの背景情報と参考ページを足すときに
migration をやり直さないため。
